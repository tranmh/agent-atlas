# agent-atlas: add MCP to the five scenarios

## Context

agent-atlas (milestones M0–M8 on `main`) shows A2A: orchestrators delegate tasks to agents through
agentgateway. The user wants the five scenarios extended with **MCP**, so the demo also teaches the second
protocol and the contrast between them:

- **A2A** = agent ↔ agent: delegation of tasks with a lifecycle (submitted → working → completed).
- **MCP** = agent → tool/data: function calls, resources and prompts offered by a server.

Both go through the same agentgateway, which understands both protocols and applies policies to both.

Decisions taken with the user:

| Topic | Decision |
|---|---|
| Who calls MCP | Worker agents. Scripted agents call tools/resources at fixed script steps. Each scenario's LLM agent lets **qwen3 choose the tools** via function calling (scripted fallback). |
| Servers | **Own Go MCP servers** with the official Go SDK (`github.com/modelcontextprotocol/go-sdk` v1.8.0), deterministic domain data from the scenario YAML. |
| Gateway | **One MCP route per scenario** (`/mcp/<code>`) multiplexing that scenario's servers (tool names prefixed per server), with a CEL MCP authorization policy. |
| Features | Tools + tool authorization, Resources, Progress notifications, Prompts. |
| Map | MCP servers at **real places**, own **hexagon** shape. Tool calls fly agent → gateway hub → server. |
| Servers per scenario | **Two**: a data server (tools, resource, prompt, a slow tool with progress) and an operations server (one allowed tool, one write tool the policy denies). 10 servers total. |
| Identity | `X-Caller` header (as on the A2A routes); CEL rules combine it with `mcp.tool.*`. |

Verified before planning:

- agentgateway v1.6.0: `routes[].backends[].mcp.targets[]` with `mcp: {host, port, path}` (Streamable HTTP),
  `statefulMode: stateful|stateless`, multiplexing prefixes tools with `<target>_`, `routes[].policies.mcpAuthorization.rules[]`
  (CEL with `mcp.tool.name`, `mcp.tool.target`, `mcp.resource.*`, `mcp.prompt.*`, `mcp.methodName`); denied tools are filtered
  out of `tools/list`.
- `qwen3:1.7b` on Ollama does OpenAI-style function calling reliably: 3 of 3 runs returned a sensible `tool_calls`
  entry with valid arguments in 3.4–6.7 s (`reasoning_effort: none`).
- Go SDK: `mcp.NewServer`, `mcp.AddTool[In,Out]`, `Server.AddResource`, `Server.AddPrompt`, `mcp.NewStreamableHTTPHandler`;
  client `mcp.NewClient(...).Connect(ctx, &mcp.StreamableClientTransport{...})`, `ClientSession.ListTools/CallTool/ReadResource/GetPrompt`;
  progress via `req.Session.NotifyProgress` with `req.Params.GetProgressToken()` and `ClientOptions.ProgressNotificationHandler`.

To be verified in the M9 spike (with fallbacks): CEL access to `request.headers` inside `mcpAuthorization`; the shape of a
denied `tools/call` (HTTP 403 vs JSON-RPC error); progress notifications passing through the multiplexed gateway session;
resource URIs and prompt names under multiplexing; which `mcp.*` fields the access log carries.

## Design

### Scenario format (single source of truth, `internal/scenario`)

New top-level list per scenario, validated like the rest (exactly two servers, one `data` and one `ops`; ids prefixed with
the scenario code; exactly one restricted write tool on the ops server):

```yaml
mcp_servers:
  - id: sc-historian
    role: data                       # data | ops
    name: Plant Historian
    description: Sensor trends and manuals of the Foz do Iguaçu plant.
    city: Foz do Iguaçu
    country: BR
    lat: -25.53
    lon: -54.60
    tools:
      - name: read_trend
        description: Read a sensor trend
        params: { asset: string, signal: [bearing_temp, vibration, oil_pressure], days: integer }
        result: "{{signal}} of {{asset}} over {{days}} days: rising, +18 K vs. normal."
        data: { max: 92.4, normal: 74.1, unit: "°C" }
      - name: full_scan               # the slow tool: progress notifications
        description: Scan all sensors of an asset
        params: { asset: string }
        progress: { steps: 5, every: 1s, say: "Scanning sensor group {{step}}/{{steps}}…" }
        result: "Scan of {{asset}}: 2 anomalies (bearing B3, oil pressure)."
    resources:
      - uri: historian://sc/manuals/turbine-t3
        name: Turbine T3 manual (bearing section)
        mime: text/markdown
        text: "…"
    prompts:
      - name: diagnose
        description: System prompt for a bearing diagnosis
        text: "You are a hydro turbine diagnostics engineer… Use the tools before answering."
  - id: sc-erp
    role: ops
    tools:
      - { name: check_stock, … }
      - { name: restricted_shutdown_turbine, write: true, … }   # denied by the gateway policy
```

Agent script steps gain:

```yaml
- { tool: { server: sc-historian, name: full_scan, args: { asset: T3 } } }          # scripted call
- { resource: { server: sc-historian, uri: "historian://sc/manuals/turbine-t3" } }   # resources/read
- { tool: { server: sc-erp, name: restricted_shutdown_turbine, args: {…} }, expect: denied }
- llm: "…"                       # existing LLM step, now with:
  tools: [sc-historian, sc-erp]  # MCP servers whose tools the model may call (via tools/list through the gateway)
  prompt_from: { server: sc-historian, name: diagnose }   # prompts/get supplies the system prompt
```

Per scenario (same shape everywhere): the **LLM agent** fetches its prompt, lists tools and lets qwen3 call 1–2 tools;
the **multi-turn agent** reads a resource; the **long-task agent** calls the slow tool (progress); the **restricted agent**
tries the denied write tool, then uses the allowed ops tool.

Proposed placements (tuned during implementation; away from the crowded Central EU cluster):

| Scenario | Data server | Ops server |
|---|---|---|
| sc | Plant Historian, Foz do Iguaçu | ERP / spare parts, São Paulo |
| ex | Tariff & sanctions DB, Luxembourg | Order management, Montreal |
| pm | Mill historian, Jyväskylä | Maintenance system (CMMS), Oulu |
| tr | Flight inventory (GDS), Madrid | HR & travel policy, Hamburg |
| kh | Document store, Dublin | Translation memory, Seoul |

### MCP servers (`cmd/mcpserver`, `internal/mcpserver`)

One Go binary, `MCP_SERVER_ID` selects the server from the embedded scenarios (same pattern as `cmd/agent`).
Built on the Go SDK: typed tools from the YAML params, deterministic templated results, progress notifications for
`progress:` tools, resources and prompts. Streamable HTTP at `/mcp` (stateful sessions), `/healthz`, `--healthcheck`.
A middleware reports what arrives behind the gateway (`mcp_server_call` event with headers + JSON-RPC body), like the
agents' `capture`. No published ports.

### Gateway (generated by `cmd/atlasgen`)

Per scenario one route:

```yaml
- name: sc-mcp
  matches: [{ path: { pathPrefix: /mcp/sc } }]
  policies:
    urlRewrite: { path: { prefix: /mcp } }
    authorization:            # HTTP level: only this scenario's agents
      rules: [{ allow: 'request.headers["x-caller"].startsWith("sc-")' }]
    mcpAuthorization:         # MCP level: never the restricted write tool
      rules: ['!(has(mcp.tool) && mcp.tool.name.startsWith("restricted_"))']
  backends:
  - mcp:
      statefulMode: stateful
      targets:
      - { name: historian, mcp: { host: sc-historian, port: 8070, path: /mcp } }
      - { name: erp,       mcp: { host: sc-erp,       port: 8070, path: /mcp } }
```

Exact CEL wording and target names are fixed by the M9 spike. `compose.agents.yml` gains 10 `mcpserver` services
(gateway `depends_on … restart: true` as for agents).

### Agent side (`internal/mcpx`, `internal/script`)

- `internal/mcpx`: MCP client per execution through `http://agentgateway:3000/mcp/<code>` with the Go SDK, an HTTP
  transport that adds `X-Caller`, `X-Run-Id`, `traceparent` and captures the wire (JSON responses and SSE streams,
  including `notifications/progress`). Generalise the capture code in `internal/a2ax/transport.go` (SSE tee, payload
  events) into a shared `internal/wire` helper instead of copying it.
- `internal/script`: new step kinds `tool` and `resource` (with `expect: denied`); the LLM step does
  `prompts/get` (optional), `tools/list`, sends the MCP tools as OpenAI `tools`, executes up to 2 rounds of
  `tool_calls` via MCP, then asks for the final answer. Any failure → scripted fallback (as today). The streaming agent
  streams "Calling tool … / Tool answered …" as A2A status updates, so A2A and MCP interleave visibly.
- `internal/llm`: request/response types for `tools` and `tool_calls`; test with a fake server.

### Events (`internal/events`, `docs/events.md`, `web/src/events/schema.ts`)

New kinds: `mcp_request`, `mcp_response`, `mcp_progress`, `mcp_denied` (agent side, wire), `mcp_server_call`
(server side), `llm_tool_choice` (the model picked a tool, with arguments). `gateway_access` gains MCP fields
(`mcp.method`, tool name/target) in the visualizer's OTLP decoder; MCP rows route to the server pin.

### UI (`web/`)

- Pins: MCP servers as **hexagons** in the scenario colour with a `⚒` glyph, label, status pulse when called.
- Flights: style `mcp` (double-dash line) agent → hub → server and back; progress notifications as small dots like SSE
  frames; denied calls stop at the hub with ✕ and "MCP denied".
- Event list: new filter group **MCP**; payload explanations for every MCP kind; agent panel shows a server's tools,
  resources, prompts (and for agents: which MCP servers they use).
- Legend: MCP line style and hexagon; one sentence "A2A = agent ↔ agent (tasks), MCP = agent → tools & data".
- Gateway panel: MCP rows with tool name and target.

In the UI: hexagon pins for 10 servers; MCP flights through the hub; a progress tool shows dots; the restricted write tool
stops at the gateway; the LLM agent's payload panel shows the model's tool choice and the MCP `tools/call` it caused.

## Risks

- **Progress through multiplexing**: if the gateway does not forward `notifications/progress`, fall back to a stateless
  per-server route for the slow tool, or show progress only from the server-side events (documented).
- **Header in `mcpAuthorization`**: if `request.headers` is not available there, keep the caller check in the HTTP-level
  `authorization` policy and use `mcpAuthorization` only for tool names.
- **Small model tool choice**: qwen3:1.7b picked a sensible tool 3/3 times; still keep max 2 rounds, a 45 s budget, argument
  validation against the tool schema, and the scripted fallback.
- **Map crowding**: 10 more pins; placements chosen outside the Central EU cluster; hexagons smaller than agent pins.
- **Run time**: tool calls add ~5–15 s per scenario at speed 1; acceptable for a "slow enough to follow" demo.
